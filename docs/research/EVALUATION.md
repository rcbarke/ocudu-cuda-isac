# Evaluation protocol

## Questions and controls

1. How does each receiver stage change sensing at a fixed pilot allocation? Match noisy realizations and antenna calibration, then compare O1, O2 and actual O3 with O0 as an offline reference. Measure false alarms and missed targets as well as error when detected.
2. Which model meets a sensing deadline under actual communication load? Use the same causal histories, features, target definitions, training splits and compute/tuning budgets for the adapted CNN, GRU and compact Transformer. Compare classical, shrinkage and learned covariance using a common calibrated angle estimator. Include mask-aware delay–Doppler, Bartlett and MUSIC, and a calibrated CFAR baseline.
3. Which deployment supports the greatest workload while sustaining PHY and sensing service? Start with a matched absolute workload. Then sweep load and compare feasible ranges. MPS on a full GB300 versus MIG on the same station identifies isolation effects independently of platform speed. DSP-only, AI-only and transport-only runs identify service and copy costs.
4. Which reference signal supports sensing at the same radio cost, and does a replayed UE stand in for a connected one? Hold the scene and target fixed and vary the source (PUSCH, PUCCH, PDSCH and PDCCH reference signals). Then hold the source fixed and compare the replayed Sionna RT radar CFR, which needs no UE, core or PRACH procedure, with an OAI software UE on the same channel. Report occupied bandwidth, cadence, resolution and ambiguity beside detection.
5. Does the result survive a change of split, memory path or host? Replay the same episodes at each functional split, vary one memory or sharing control at a time, and run the same core on Aerial Framework and on Aerial-OCUDU over the air. A change in the observation record is located before the model is examined.
6. What does a joint objective cost each side? Sweep the communication weight of the joint model and report the sensing endpoint, estimate error, executed-receiver block error rate and execution cost for every trained point.
7. What does compiling the sensing chain buy, and does it change a decision? Run the Python reference and the native core on identical records, weights and arms. Report the latency of each by the same boundaries, the agreement of their decisions at the frozen threshold with every flip listed, and the PHY tails beside each.

## Endpoints and denominators

Let W cover the interval from the first to the last contributing RF sample. Report acquisition, post-window latency and their sum L from the first sample to result publication. At a predeclared false-alarm target, record the fraction of all eligible target-present opportunities with a detection inside physical-error tolerances and L ≤ D. A late, missing, dropped, abstaining, or invalid answer cannot succeed. Count a target-absent false alarm whenever an eligible absent opportunity triggers a positive; report missing absent opportunities separately, since overload could conceal false alarms. State whether an opportunity is a window, a slot or an episode. Also report per-episode totals. Where a model outputs a location, report position error in metres over eligible present opportunities (mean, median and 90th percentile, raw and smoothed) with its denominator. Position error never replaces the detection endpoint, because a location is only defined when a target is present.

For communication, report scheduled TBs, true CRC outcomes, payload mismatches, offered payload per second, and correctly decoded data bits per unit wall time. Declare retransmission and unique-payload rules. PHY misses use the actual scheduled release plus the configured processing allowance, including late or unfinished jobs in the denominator. The allowance and every sensing deadline are derived from calibration runs by rules fixed in advance (S4.6, S5.6). They are valid for the placement and host state they were measured on. Distinguish receiver goodput from application goodput through the UPF.

For timing, save sample counts, p50/p95/p99 and, if statistically supported, p99.9. Counts of uncensored scheduled work accompany latency distributions for completed work. Use per-episode or session-clustered paired intervals. For rare-event claims show the event count and interval; with zero events over N independent opportunities a one-sided 95% upper bound is about 3/N. Adjacent slots can be correlated. Record temperature, throttling, clocks, warm-up, and run order. Report both nodes' total energy for M2 and calculate joules per timely correct estimate from system energy and the actual number of successes. A latency, a deadline, a contention effect or an energy figure is reported from a run whose sensing runtime is the native core, with a native unit for every stage. A run on the Python reference reports its latency with that label and supports accuracy endpoints only. [Code levels](../architecture/RUNTIME.md#claims-and-the-evidence-each-needs)

Three objective families are reported side by side and never summed into one score: sensing (timely detection at the fixed false-alarm point, physical and position error), communication (true CRC, block error rate, goodput, PHY misses) and execution (latency tails, copies and bytes moved, memory, energy).

## Prevent shortcuts in training and evaluation

Split by geometry, trajectory or capture session before windowing. Keep paired present/absent realizations and all overlapping windows in the same split. Fit scalers, clutter templates and threshold on training/validation data only. Hide target-specific paths, geometry truth, future outcomes, file names carrying class, and truth IDs from features. Require the same false-alarm calibration procedure per method. Apply a fixed pilot mask and representation across deployment comparisons, then run payload/quantization sweeps as separate experiments. Validate DOA under stated covariance sample count, model order, steering convention, and calibration. An ambiguous angle, including mirror solutions of a linear array, should be scored using the declared observation geometry.

## External validity

The public PUSCH channel-estimate dataset can test front-end conventions and domain shift using its session splits and labels. Check carrier, array, axes, pilot cadence and target task before interpretation. A file of channel estimates lacks the original transmitted TBs and complete receiver timeline needed to measure CUDA-OCUDU BLER and latency. Over-the-air captures on Aerial-OCUDU are the capstone tier (S11). They have their own protocol, session splits and labels. No two captures repeat a channel, so paired receiver-stage claims stay with the replayed episodes.

## Comparison with cuSense

S11.4 scores every arm on cuSense's task (position error on runs with a person present) and on this project's endpoints (presence on present and absent runs at a fixed false-alarm point, with late results counted as failures). Latency is reported by both definitions: cuSense's, from the notification of the last slot of the window, and this project's, from the first contributing sample. A reproduced cuSense arm is labeled as a reproduction and shown next to the published figures. Published figures are a reference and not a target. In simulation and over the air the aim is comparable performance, recorded with every difference between the systems, as S1.2 did for the DeepSig Table II timing. See the [reference ledger](REFERENCES.md). The latency comparison uses native runs. The published 241 us belongs to cuSense's native serving option, CUDA preprocessing with a TensorRT engine, and the pinned sample applications publish no cuSense dApp to rerun.
