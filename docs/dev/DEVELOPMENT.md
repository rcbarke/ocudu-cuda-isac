# Implementing receiver-aware ISAC on CUDA-OCUDU

**First hardware result (accepted).** One DGX Spark builds the pinned WG1 receiver and reproduces the correctness comparison in the 20 MHz, one-layer row of DeepSig Table II. **Demonstration (next).** One UE, one layer, four RX, 20 MHz/51 PRBs at 30 kHz SCS on the same Spark. No UE or core is attached: a Sionna RT radar CFR applied at the receiver stands in for a UE transmitting through a moving-target scene. The receiver decodes the known uplink and exports its own CUDA channel estimate. A second MPS client runs a cuSense-like pipeline on that estimate and publishes a causal presence decision, a delay–Doppler view and a location map. A lightweight browser page shows the radio, sensing and system KPIs live. Deadlines and service levels are calibrated on the implementation before anything is graded against them. **Collocated study.** Bring every radar, AI, channel-source, split and memory ablation up on that one Spark under MPS. Then attach a software UE on the split-8 ZeroMQ boundary. **Systems study.** Repeat the frozen workload across two Sparks on a 100 Gb/s CX7 link and across MIG instances on a GB300. **Capstone.** Run the same sensing core on Aerial Framework. Then swap DeepSig-OCUDU for Aerial-OCUDU with the same contribution code, evaluate over the air and compare with cuSense. **Publication.** Measure how receiver processing, model choice, load and placement affect timely sensing at a fixed false-alarm operating point while preserving a specified radio service level.

**Code levels.** The receiver is changed by one patch (S5.2). Project C++ adapts each host. Sensing is a separate CUDA client, and every sensing stage that is timed runs in a native core of CUDA kernels and TensorRT engines, with no Python interpreter in the process. Python and PyTorch define each stage, train the models and serve as the parity reference. The core has no host, so the same source runs beside DeepSig-OCUDU and inside the Aerial ports. [Code levels and the native core](../architecture/RUNTIME.md) The demonstration shows the native latency: its graded branch runs in the core with a TensorRT engine. The live showing needs D4. S4.3's archived evidence run (three paired repetitions on 20 held-out episodes) can follow the showing and closes the ticket. Every Unit gate applies in full.

**The receiver's estimate is in the demonstration.** S5.2 keeps its number and is built here, on the staged harness. The pinned kernel already holds the estimate on the device after pilot LS, frequency interpolation and smoothing, per DMRS symbol, and the pin declares a diagnostic accessor for that buffer. That is the stage cuSense reads from Aerial. The work is a read-only route from the GPU demodulator to the observer, an ordered copy and the parity check. The patched receiver is built from a separate worktree into its own build directory, so the submodule stays pristine and the accepted S1.1 build is the hook-free control. O2 stays as the parity reference and as the fallback input.

**No UE is attached.** The demonstration has no UE, no 5GC and no PRACH procedure. A Sionna RT radar CFR applied to a legal grant at the receiver stands in for a connected UE transmitting through the scene. S6.10 later checks that shortcut against a software UE, and M5 against commercial UEs.

**Comparable, not replicated.** The demonstration measures this simulation. Position error and latency are recorded beside cuSense's published figures and are not graded, exactly as S1.2 recorded Table II timing beside the paper's. The published position error belongs to one room and one over-the-air system and is not a target.

**Deadlines are calibrated, not assumed.** The 5 ms and 50 ms sensing deadlines and the radio allowance are starting proposals. S4.6 measures the implementation, derives them by rules fixed in advance and verifies them on a second run before any held-out episode is read. S1.2 timing was accepted with host tuning deferred, so the demonstration's values hold for the recorded host state. S5.6 tunes the host and recalibrates for the paper, and every later placement repeats the calibration as its first Integrate step.

**The demonstration shows native latency.** The graded cuSense-like branch runs in the native core (S3.6): CUDA kernels for the front end and a TensorRT engine for the model, in `sense_host`, the second MPS client, with no Python in the process. Its latency is shown on the page by cuSense's boundary and end to end, beside the same pipeline on the Python reference, and is recorded beside cuSense's published 241 us without being graded. The demonstration requires the TensorRT backend, so the probe of S3.6 runs first (D0). If the Spark has no TensorRT build for its CUDA stack, the native showing is blocked. The LibTorch backend then keeps the pipeline running, is named on the page and does not stand in for the TensorRT result. The delay-Doppler branch stays on the reference runtime until S6.12. In the timed arms it runs on the CPU, outside the PHY CPU set, so that the receiver and `sense_host` are the only two CUDA clients. [Runtime axis](../architecture/RUNTIME.md#runtime-axis)

### Added by the first observer run of 2026-11-21

The accepted Sprint 3.1 run measured 1,471 us for one observation of 4 by 2 by 306 estimates, against a slot of 500 us. The estimate itself is a small part of that. The rest is SHA-256: the observer takes the digest of the whole grid after its read, 274 kB through the grid reader, and the digest of its payload. The harness of Sprints 2.3 to 3.1 hashes the same grid seven more times per opportunity, on purpose, because those gates prove bytes. None of it is Python, and none of it is inside a PUSCH service time that was reported: that clock runs from the start of a decode to the decoder's callback. A hash proves correctness offline. It has no place between a grid and a deadline. "Before" is the state of the accepted Sprint 3.1 tree.

| Requirement | Before | Built in |
|---|---|---|
| **No checksum in a timed path** (decided 2026-11-21). From the moment a grid is ready to the decoder's callback, and from the observer's read to the publication of its record, a timed run computes no SHA-256 and no other checksum, reads no grid back in full, writes no file, formats no text and allocates nothing. A timed run is every run whose latency, deadline or service level is reported or shown. | Eight digests of the whole grid per opportunity in `pilot_ls`, one of them in the observer, and one digest of the payload | S3.2 for the observer and the ring, S4.1 for the staged harness, S5.1 and S5.3 for the DU, where no harness exists and only the observer path remains |
| **Two evidence modes, one arithmetic.** `audit` is what the gates of S2.3 to S3.1 run: every digest, every stored grid. `timed` leaves the digests to the evaluator, which takes them from the archived payloads after the run. The same plan in both modes must give the same payload bytes and the same decoded bytes, so the timed path is shown to compute what the audited path computes. | One mode | S3.2 (`pilot_ls`, the observer and the ring), S4.1 (the launcher names the mode of every arm) |
| **Ownership by generation, not by content.** In a timed run an observation is tied to its grid by the ticket of the fill, the grid index and its generation, and the ring's generation counter guards a slot. A changed grid is found by the audit mode and by the offline digest, never by a hash in the slot. | The observer records an estimate only when the grid has its readback digest again | S3.2 |
| **Join keys before the run.** The opaque 64-bit keys of an episode, an opportunity and a grant are hashed when the plan is bound, not per slot. | Three short SHA-256 per observation | S3.2 |
| **The cost of the tap is measured and has a ceiling.** The observer's service time, from its read to its completed record, is recorded per observation on the Spark at the demonstration profile, and no call of the hash is counted in the timed mode. Ceiling until S4.6 calibrates it: 150 us in the mean and at the largest value. Expected from the breakdown below, measured on the Spark: about 10 us for the estimate and the record, to which the publish of S3.2 is added. | 1,467 us in the breakdown, 1,471 us in the accepted run | S3.2 gate, calibrated in S4.6 |

### Added by the process-layout review of 2026-11-21

The review asked one question before Sprint 4.1: should the receiver and the sensor stay two queued processes under MPS, or should the sensing kernels and the TensorRT engine run on a stream of the receiver's own context in one process? It compared the plan with the cuSense paper, the two OCUDU dApp platform papers, the MPS documentation and the pinned receiver. The two-process layout is confirmed for the demonstration and for both papers, and three parts of it are tightened. "Before" is the state of the accepted Sprint 3.1 tree. [Process layout, with the comparison and the prior systems](../architecture/RUNTIME.md#process-layout)

| Requirement | Before | Built in |
|---|---|---|
| **Two processes on every DeepSig-OCUDU placement** (confirmed 2026-11-21). The receiver and the sensor are two MPS clients on one Spark, two hosts over CX7, two GPU instances on the GB300 and an L1 with a dApp on Aerial-OCUDU. No ticket puts sensing on a stream of the receiver's context. The single process shortens the hand-off by about 100 us against a sensing budget of milliseconds, removes no contention, and exists on one placement only. | Stated in several places without the comparison | S4.1. Unchanged in S5, S7, S8 and S11.2. S10.2 is the one in-process host, by the Framework's design. |
| **One queue, first in, first out, with no system call in the producer.** The ring is the only queue between the receiver and a sensor. Record `sequence` n lies in slot n modulo the slot count. Admission is two loads and a compare, publication is one store, and credits come back through a count that the consumer advances in its own page. The control channel carries no message per observation. | A slot pool, a socket message per publication and a socket message per release | S3.2, [ring contract](../interfaces/OBSERVATION.md#the-ring-obs-ringv1) |
| **The sensor of a timed run does not sleep on the data path.** Wait mode `spin` on the sensor's own core. `wait`, on an eventfd, serves gates and tests that reserve no core. | Socket notification by default, polling as a later factor | S3.2, S4.1. Compared in S5.5. |
| **Depth follows the window, never the backlog.** Slot count: the records a plan holds in place, plus one uplink burst, plus one, rounded up to a power of two. Eight for the O3 stream of the demonstration. A sensor more than one window behind skips to the newest complete window and counts what it passed. | Slot count taken from the profile, no rule | S3.2, S3.6 |
| **One GPU submission per window.** The sensor makes no CUDA call while a window is open. At the last record it runs ingest, kernels and engine once, on one stream. | Not stated | S3.6 |
| **MPS is proven and time slicing is refused.** An arm is labeled MPS only when both process IDs are in the server's client list. On the Spark the sensor's context is created before the receiver starts. | "Reject an unverified server/device pair" | S4.1 |
| **Contention is handled on the sensor's side, in a fixed order, and never by queue depth.** Baseline `mps_default` with release `immediate`. If the concurrent arm moves the radio's tail beyond the rule of S4.6: sensor client priority, then a ceiling on the sensor, then release `after_radio`. One at a time. | The MPS controls were a matrix of S5.5 only | S4.1 for the demonstration, S4.6 for the rule and the freeze, S5.5 for the sweep |
| **The cold start is apart** (decided 2026-11-23). The first use of a receiver process is a decode of the lead-in of its run and never a release of its schedule. Every latency, tail, count and goodput of the demonstration and of the paper is computed on the releases of a schedule, from `radio/` and `pacing/releases.jsonl`. The cold start is reported as a figure of its own, from `pacing/lead_in.jsonl` and `cold_start` of the record, with the loss that a schedule without a lead-in showed. A run without a lead-in is labeled cold and is never pooled with a warm run. | The first decode of every run was left out of the service statistics, and its two skipped releases and the lost first window stayed in the counts | S4.1 (the lead-in), S4.2, S4.3, S4.6, S5.5, S5.6 |
| **Two decodes are compared by their input, and never by equal decisions** (decided 2026-11-23). The receiver's estimate is not bit-reproducible between two decodes of one grid (S5.2), and the frozen threshold is the logit of a validation window. Where two arms or two runs score the same grid, a window is compared by the digest of the input its sensor was given: the same input bytes give the same logit within 1e-6; two decodes that differ give logits within a tolerance declared before the run; a decision that differs inside the bound of its window is a flip at the threshold, listed with both margins. A count of detections or false alarms states how it treats a window inside that band. | The gate asked for equal decisions in every window, which held in three runs by chance and failed in the fourth on one window of 960, 9.2e-05 from the threshold | S4.1 (`decisions` of the record), S4.2, S4.3, S4.6, S6.11 |
| **The in-process placement is measured as a control cell** (scheduled 2026-11-21). `placement: in_process`, staged harness only, same core, plan and engine, after the demonstration. It is measured by the method of the cuSense paper, step by step, beside the two-process cell, so that the cost of the export path and the worth of the process boundary are stated on one GPU. It is a control and not a deployment. | "Not scheduled", undefined | S5.5, [RUNTIME.md](../architecture/RUNTIME.md#the-in-process-control-cell) |

Why the queue is specified this tightly. The OCUDU dApp platform measured its own ring, of the same kind, on a GB10: 1.97 us per publication at the median in both conditions, but 2.34 us on a quiet host against 167 us with a cell on the air at the 99.9th percentile, with three system calls per publication, and a wake of the sleeping consumer of 99 us against 1,620 us. Why the sharing mode is proven. cuSense measured 58 us for a native TensorRT step on a Spark under MPS and about 0.5 ms, with tails up to 1.3 ms, under time slicing. Neither paper reports what the sensor does to the radio's tails. S4.1 and S5.5 do.

Four rules keep the axes independent.

1. **The sensing core has no host.** `src/ocudu_cuda_isac/sensing/` imports no OCUDU binding, no Sionna package and no adapter. It consumes the observation record and returns decision records. An import test enforces this from S3.3 on. `native/sense_core/` obeys the same rule at link time: no OCUDU archive, no Aerial library and no Python library (S3.6).
2. **Each host is an adapter.** `native/ocudu_adapter/` serves DeepSig-OCUDU at every split. `adapters/aerial_framework/` (S10) and `adapters/aerial_ocudu/` (S11) emit the same observation record and accept the same decision record.
3. **Simulation stays offline.** Sionna and Sionna RT are used in `src/ocudu_cuda_isac/episodes/` and in training. No slot loop calls them.
4. **Timed stages are compiled.** Python and PyTorch define a stage, train it and check it. A stage that a run times executes as a CUDA kernel or a TensorRT engine in the native core, under the same registry name, with a parity test against its reference. From S3.6 on, an Integrate step that reports sensing latency, a deadline, PHY tails under sensing load or energy runs `runtime: native`. [Code levels](../architecture/RUNTIME.md)

## How to implement and sign off one ticket

1. Select the card, its production owner and fixtures. Open one patch against the named package or native target. Resolve the exact upstream symbol and commit first. Reuse OCUDU's grants, PUSCH and CRC, Sionna's NR generator/ISAC primitives, RT's solvers, library FFT/eigensolvers and PyTorch layers. Commit small fixtures or their creation recipe with an independent expected answer.
2. Implement the production interface and run its focused unit test inside this checkout's `isac`. Inject a test clock, fake grid/transport or small tensor as specified. A component can be **unit accepted** before any hardware integration. Upstream whole-project integration suites are separate from building an individual adapter.
3. When the integration prerequisites exist, run the real producer and consumer. Grade against the named observable. Archive a unique run ID, command, inputs, toolchain/commit/patch hashes, raw logs, counts, judgment and reason. Preserve failed attempts. Record a blocked host or missing optional system explicitly. A skip, zero executed cases, a dry run or a fallback cannot close the requested hardware gate.
4. Mark the sprint **integrated** only with its real evidence. Keep unit and integration status separately in the issue/PR. For studies, a correctly measured adverse result completes the experiment. Passing a functional gate never implies a published speedup or service level.

**Command contract for future tickets.** The S2–S9 card heading gives a selector. Each implementing patch provides a directly executable `tests/unit/test_<selector>.py` with a `unittest.main()` entry point and a matching `tests/integration/<selector>.py` plus `configs/integration/<selector>.json`. Create the specific files with the feature. The native adapter may use a small CMake/CTest target with a fake interface and a thin Python test wrapper. Production C++ should build against the locked headers, and CPU-only unit targets should link only their module and doubles. Each integration driver takes `--config FILE --output-dir DIR`, refuses to overwrite an existing run, and writes a grade with an explicit case count. The two commands below exercise S3.1 after implementation.

```sh
python tests/unit/test_pilot_ls.py -v
python tests/integration/pilot_ls.py --config configs/integration/pilot_ls.json \
    --output-dir results/runs/s31-spark-001
```

These are build contracts for future patches. Runnable commands in S0/S1 are identified below. Keep hardware drivers outside default unit discovery and make each hardware command opt-in. Use `tests/unit/__init__.py` for discovery when adding the first future unit module. Never count an absence of imported tests as a successful gate. From S3.3 on, `tests/unit/test_core_imports.py` asserts that `ocudu_cuda_isac.sensing` imports no host adapter, OCUDU binding or Sionna package. [Evidence format](REPRODUCE.md)

**Reference and native entries.** A sensing ticket delivers the Python reference of its registry entries, with the hand-checkable vectors of its Unit field. The ticket that adds the native unit (S3.6, S6.12, S6.13) runs the same vectors in CTest and, through the binding, in `tests/unit/test_<selector>.py` beside the reference. `tests/unit/test_core_link.py` asserts that the native core links no OCUDU archive, no Aerial library and no Python library. `scripts/native_core.py` builds the core into its own build directory. The OCUDU adapter's build never compiles it.

- **Integrate.** Run the held-out episodes through both stacks. Report estimate NMSE between receivers, detection at the fixed false-alarm point per receiver and the change when a model trained on one receiver is tested on the other.
- **Accept.** `receiver_parity.json` holds paired IDs, coverage with denominators, the estimate and decision comparisons and each stack's revision. This is the receiver-domain shift measurement that S11 carries over the air.

## S11 · Go over the air on Aerial-OCUDU

Every simulated result is produced on DeepSig-OCUDU. Going over the air means swapping DeepSig-OCUDU for Aerial-OCUDU, the OCUDU branch that pairs OCUDU's L2 with Aerial's L1 over FAPI, and carrying the contribution code across. This phase starts when the WNC O-RU and the Fibrolan Falcon-RX grandmaster are received. Until then its Integrate steps are recorded as blocked on hardware, and its Unit work proceeds on recorded data.

### S11.1 Swap the host and prove it without project code · `aerial_ocudu_baseline`

- **Build.** Add Aerial-OCUDU as a fourth dependency in `ext/lock.json`, with its repository, branch and commit, and record the Aerial L1 release and the FAPI bridge it needs. Add launch profiles in `experiments/aerial/` for the WNC O-RU on CX7 fronthaul with the Falcon-RX as the G.8275.1 grandmaster with SyncE, an OAI 5GC unless the testbed uses another core, and Pixel 7 UEs. Record which parts of the contribution move. The sensing core, the record schemas, the scorecard, the KPI stream and the page move unchanged. The scheduler binding of S5.1 moves with OCUDU's L2. The native PHY observer does not move, because Aerial's L1 replaces OCUDU's PHY, and S11.2 supplies the observation instead. [Aerial ports](../integration/AERIAL.md)
- **Unit.** The pin check covers the four dependencies and the two reference sources and refuses a build that mixes the two OCUDU trees. A launch profile is refused while the PTP state is not locked or the fronthaul link is not at its declared rate. The contribution's import test passes in the Aerial-OCUDU environment. A run without a registered UE is labeled load-only.
- **Integrate.** Bring the cell up with no project code attached. Register a Pixel 7, establish a session and carry uplink traffic. Record PUSCH CRC and block error rate, slot deadline misses, application goodput and the PTP offset. Run the S4.6 calibration on this host before any sensing run.
- **Accept.** `aerial_ocudu_baseline.json` names every revision, the O-RU, the timing source, the UE and the core, with the radio outcomes and the calibrated service levels. This is the hook-free control for the rest of S11, as the S1 build is for DeepSig-OCUDU. Expect performance comparable with the simulated baseline and record the differences. Do not expect a match.

### S11.2 Consume the L1's estimates as a dApp · `e3_dapp`

- **Build.** In `adapters/aerial_ocudu/`, write a dApp that subscribes through E3 to the PUSCH DMRS estimates, SRS estimates, frame information and resource allocation, reads the payloads from the shared-memory buffers the indications reference, and maps them to the S3.2 observation record. Aerial exports the DMRS estimate after frequency interpolation and before time interpolation, the same stage as O3 on DeepSig-OCUDU, so the cuSense-like input contract is unchanged. The dApp logic is the native core of S3.6, rebuilt for the host and attached behind the `e3::InferenceEngine` interface of the pinned sample applications (`dapps/common/e3_manager/inference_engine.h`). The adapter turns the shared-memory row that an indication references into an observation view with the `aerial_hest_c64` layout. Add a replay mode that reads recorded data with its original timestamps. Start from NVIDIA's sample dApp structure and keep its license notice. Confirm on the system that the E3 Agent serves these streams when the L2 is OCUDU.
- **Unit.** A fabricated ping-pong buffer pair with one indication each yields two observations in order, and a reference to a buffer that has since been overwritten is rejected by generation. A TAI timestamp converts to UTC with the stated 37 s offset. A PUSCH allocation that starts at PRB 10 is placed at subcarrier 120. Three UL slots of one DDDDDDSUUU period form one window and a fourth slot from the next period does not join it. The public H-estimate release loads through the replay mode with its 3,276 subcarriers, four RX ports and three DMRS occasions.
- **Integrate.** Replay the public dataset through the dApp offline. Then run live against the E3 Agent, with the dApp sharing the GPU through MPS and, on hardware that supports it, in its own MIG instance. Record indication-to-publication latency and the copy cost reported by the framework. Compare CRC and deadline misses with the S11.1 control.
- **Accept.** `dapp_run.json` names the revisions, the subscribed streams, the GPU sharing mode and the latency distributions, with the observation counts reconciled against the indications received.
- **Rehearsal, built in M1.** The port is proven on the Spark before any Aerial hardware. `scripts/export_e3_trace.py` writes the O3 records of a DeepSig-OCUDU run, with their allocations and radio outcomes, as the PUSCH metric and channel-estimate streams of a trace in the format of `cuPHY-CP/e3agent-standalone/docs/trace_format.md` in the pinned Aerial tree. The O3 payload is transposed and widened from `ocudu_o3_fp16` to `aerial_hest_c64`, and nothing else is changed. The standalone agent, built in its own container from that tree, replays the trace into its shared memory, and the dApp subscribes as it would to a live L1. Its decisions must equal those of `sense_host` on the same records: equal counts, scores within the widening tolerance, and every flip listed. Archive `port_rehearsal.json` with both revisions, the trace hash and the agreement. A host without a container runtime records the rehearsal as blocked.

### S11.3 Capture labeled over-the-air episodes · `ota_capture`

- **Build.** In `src/ocudu_cuda_isac/episodes/ota.py` and a lab protocol under `experiments/ota/`, define indoor captures with the WNC O-RU and Pixel 7 UEs: target-absent runs, target-present runs with an independent position label (surveyed track or camera), array and timing calibration, and whole runs assigned to training, validation and held-out sessions. Reuse the S6.8 capability table.
- **Unit.** A fabricated session with a label gap, a clock offset between label and radio time and one unlabeled run yields the eligible count, the applied offset and no negative example from the unlabeled run. A run that appears in two splits is rejected. Radio and label clocks without a recorded mapping make the capture ineligible for latency claims.
- **Integrate.** Collect at least the run structure cuSense used, with target-absent runs equal in number to target-present runs. Verify label alignment on a calibration walk. Archive raw estimates, I/Q where the stream is subscribed, labels and the room survey.
- **Accept.** `capture_manifest.json` per session with stack, RU, bandwidth, antennas, UE, labels, calibration, splits, hashes and limits. Consent and privacy handling for any camera data is recorded before collection.

### S11.4 Compare with cuSense and carry traffic · `cusense_comparison`

- **Build.** In `experiments/aerial/`, define the comparison. Arm A is cuSense as published, reproduced from the paper unless NVIDIA supplies its checkpoint, and labeled accordingly. Arm B is the S3.5 pipeline retrained on the same training sessions. Arm C is the best classical chain and learned model from protocol A. Score all arms on cuSense's task (position error on present runs) and on this project's endpoints (presence at a fixed false-alarm point on present and absent runs, timely success from the first contributing sample). Sense on the scheduled PUSCH of registered Pixel 7 UEs that carry user-plane traffic.
- **Unit.** The pair checker rejects arms trained on different sessions, normalization fitted outside the training split for arms B and C, and a latency comparison whose arms use different start boundaries. A three-run toy set reports position error only over runs with valid labels and reports the excluded count. A goodput row without verified payload delivery at the far end is refused.
- **Integrate.** After S11.2 and S11.3, train and freeze every arm before the held-out sessions are read. Run each arm live as a dApp and in replay, with the dApp off and on. Report latency by cuSense's boundary and by this project's boundary side by side, with block error rate, application goodput and slot deadline misses.
- **Accept.** `cusense_comparison.json` holds the arms, training sessions, frozen hashes, both endpoint families with denominators and intervals, the two latency definitions and the joint radio outcome. Published cuSense figures are shown beside the measured ones as a comparison that is not graded. The room and the hardware differ, so comparable performance is the expectation and an exact match is not.
- **Runtime.** Every arm runs `native`. The pinned sample applications (v1.2.0) publish three PRB-power dApps and no cuSense dApp, checkpoint or native engine, so arm A stays a reproduction from the paper until one is published and pinned. Latency by cuSense's boundary is compared with the published figure of its native serving option.

## Where to start when a gate fails

| Observation | First discriminating check |
|---|---|
| CUDA was configured but CPU and GPU appear identical in the log | Check the build cache, CUDA targets, binary identity, actual residency counters and completed decodes on the measured row. |
| CRC passes but the captured estimate is zero | Inspect the active producer. Validate O2 against known pilots, then inspect O3's device producer, event ordering, precision and lifetime. |
| Presence fires on absent scenes | Inspect the physically absent background, held-out split, training-only normalizer, invalid-mask handling and runtime feature allowlist. |
| The presence head scores differently on its device and offline | Compare the input digests of the two decisions first. A different digest is a different feature: the feature lines differ before the head is involved. With equal digests compare the device and the PyTorch build in the two `presence.json` reports, then the tolerance in `configs/integration/presence_head.json`. |
| A plan of a set replay is refused with `has no bound grid`, or `presence` and `train_presence.py` leave with status 2 | The entries of an episode set bind no transmit grid: build the plan with the bindings of the reference pair (`presence_head.write_plans`). A status 2 names its rule in one line: a vector of another specification, an altered artifact, or a sample outside its split. |
| The cuSense-like model scores differently on its device and offline | Compare the input digests of the two decisions first. The front end is NumPy on the CPU on both sides, so a different digest means other records or another artifact: compare the window lines before the model is involved. With equal digests compare the device and the PyTorch build in the two `cusense.json` reports, then the tolerances in `configs/integration/cusense_frontend.json`. A location that moves between two cells of nearly the same value is listed and is no failure. |
| The S3.5 gate reports dropped estimates of the stage O3 in `live account` | The sensor did not keep the pace of the receiver on its ring. Check that it was warm before it attached (`sensor-ready.json`), then `infer_ns` and `frontend_ns` of its decisions and what else used the device. The reference sensor works through every record. Skipping to the newest complete window is the rule of the native sensor of S3.6. |
| `train_cusense.py` or `cusense replay` leaves with status 2 | The one line names its rule: a held-out row or a scene in two sample sets, samples of another specification, an altered artifact, statistics that name another split than training, or too few windows of a class for the fit or the calibration. |
| `make core-probe` fails, or the S3.6 gate stops at `D0 probe` | Read `sense-probe.json`: `tensorrt.searched` lists every place that was looked at, and `problems` names the missing part. Libraries without headers come from the wheel: run `make core-env-tensorrt`. A package installation elsewhere: export `TENSORRT_ROOT`. Headers and library of different versions are refused by the probe itself. `probe/compile.log` and `probe/run.log` hold the compiler and the engine. If no TensorRT builds an engine on this GPU, record that: the declared fallback is `scripts/native_core.py build --tensorrt off --libtorch`, and the native showing is blocked. |
| `make core-build` stops in `tools/sense_engine.cpp` or `src/engine/tensorrt.cpp` at a name that is `not a member of 'nvinfer1::...'` | The TensorRT of the host is of another generation than the sources were compiled against: `sense-probe.json` names its version and origin. The sources hold for TensorRT 10.14 and 11.5. TensorRT 11 removed `BuilderFlag::kFP16` with the weakly typed network, which stopped the first build on the Spark, and the engine builder now names that flag only where `NV_TENSORRT_MAJOR` is below 11. For a name of a later release, compare `NvInfer.h` of both releases and guard the use the same way, or build against the other installation with `TENSORRT_ROOT`. `tests/test_native_core.py` holds the rule. |
| The unit case `sense_core_device_vectors` fails or is skipped on the Spark | Skipped means the CUDA runtime reached no device: the case prints the reason. Failed with `within tolerance, not bit-identical` printed is a note, not the failure. Otherwise compare counts first: they are integers and must be equal. Then the window mean, then the input. The twin runs the same source, so a difference is the compiler or the device: check `--fmad=false` in `build.log` and the CUDA architecture in `isac-core.json`. |
| The native core and the reference disagree in `runtime_parity.json` | Read the first problem of the capture. Statuses that differ are a window question: compare `windows/windows.jsonl` of the two outputs, which are equal field by field but for the runtime entry. An input beyond its bound is a front-end question: run the same archive on `--device host --engine host_reference`; if the twin agrees with the reference, the kernels differ from their twin. Inputs within their bound and scores beyond tolerance are an engine question: compare `--engine host_reference` on the device with the TensorRT engine, check `tf32` and `precision` in `engine.json`, and run the ONNX file in ONNX Runtime. A flip is listed with its margin and fails only when the margin is larger than the tolerance of its logit. |
| `sense_host` refuses an engine | The one line names its rule: another artifact, another TensorRT version or another GPU than the manifest names, or a file that was altered. An engine is rebuilt on the GPU that runs it: `python scripts/native_core.py engine --artifact DIR --output-dir DIR`. |
| The S3.6 gate reports drops or skipped windows in the paced `live` case | The sensor did not keep the pace of the slots. Check `timing_valid`, the stages in `runtime_latency.json` and `host_state`: another process on the GPU or a busy core is recorded there. The reference sensor may drop on the same pace: its drops are counted in its feed report and do not fail the gate. |
| Radio tails grow under concurrent inference | Hold offered releases fixed. Compare tap-off, copy-only and full sensing. Use completion traces to locate the delay. |
| Apparent network or MIG gain changes with deployment | Compare timestamp uncertainty, matched payload and transport-only controls on M2. Compare per-profile isolated and full-GPU runs on the same station for M3. |
| The page shows a count the scorecard does not | Regenerate `kpi.jsonl` from the archived bundle in replay and diff it against `kpi_parity.json`. The raw events decide. |
| PHY tails grow when the page is open | Check the viewer location and the GPU client list, the aggregator's CPU set and the page-off arm of `gui_impact.json`. |
| A calibrated deadline is missed in the evidence run | Compare the host state with the one recorded in `slo_calibration.json` before changing any value. A recalibration is a new run and a new profile hash. |
| The receiver's estimate and the observer's disagree | Check the producer trace and generation first, then the smoothing stage, scale and FP16 conversion against the flat-channel fixture of S5.2. |
| The host CRC fails on a noiseless replayed grid | Check the DM-RS reference point first (CRB 0 for PUSCH; `grant_fixture --dmrs-reference prb0` reproduces the wrong one), then the receive port list (0 to N-1 in order), then the pilot amplitude against `source.json`. |
| The return is missing from the receiver's estimate, or reads as rounding noise | Check that S2.3 applied the entry's grid gain. The stored channel is physical, and without the gain the return lies below the normal range of the receiver's 16-bit floats. Then check the slot index: slots 7 and 17 alternate at 5 ms spacing and carry different DM-RS. |
| The stored grid of S2.3 differs from the Python reference | Read `comparison.json`: if the values before storage are identical, the difference is the storage rule, and `model_mismatches` in `native.json` counts it. If they are not, run `replay_core_test --digest` against the scalar reference of `grid_apply.py`, then check the gain of the plan and the grant of the opportunity. |
| `grid_apply` refuses a plan with status 2 | Its last line names the rule. A hash that differs means the stimulus changed after the plan was built: build the plan again from the entry. `no store entry` means a Sprint 2.1 or 2.2 run was moved: name its `grant_fixture` directory with `--grant-store`. |
| A flat channel reads as 1.00119, or a noiseless comparison stops near 56 dB | Both are the grid's storage: the pilot is stored with magnitude one per component against a reference of 0.998815, and every value keeps eight significant bits. Compare after rounding with `grant.bf16`. |
| A new source, split or host changes a sensing result | Compare its observation record with the staged-harness reference on common support before looking at the model. |
| The native core and the Python reference disagree | Compare the ingest first: the layout name, the element order and the FP16 widening on the `[1][3][2][5]` fixture. Then the registry name each side resolved, then the engine's precision against the frozen artifact. |
| Sensor latency moves between two runs of one profile | Read the `runtime` entry and the engine backend of both manifests, and whether the sensor process maps a Python library, before looking at the GPU. |
| The sensor reads a record that the receiver did not publish | Check the generation before and after the read, the consumer's epoch, and that the consumer's mapping is read-only. A stale read is counted and never reaches a decision. |

For each failed gate retain the fixture digest, command, failing expected/observed value, raw log and smallest subsequent rerun. Update the ticket with its separate unit and integration status.
